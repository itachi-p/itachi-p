# エージェントへの受け渡しで踏んだ失敗と検査規則

対象: itachi-p/my-acronym-app のタグ体系移行・データ整理・登録フィルタ実装
日付: 2026-08-26

DB を見られる側（ブラウザ）とコードを見られる側（ターミナル）に分かれた構成で
作業を進めた過程で発生した失敗から、次回以降に事前検査できる規則だけを抽出する。

---

### 一意でない列だけで更新対象を指定しない

- **症状**: 副タグ付与のSQLを `acronym` だけで一致させた結果、
  `SIOP | Sales, Inventory and Operations Planning` に「政治」タグが付いた。
  意図していたのは `SIOP | Single Integrated Operational Plan`（核戦争計画）だけだった。
  同様に `PPAP`（楽曲）に「経営」、`ROI | Region of Interest`（画像処理）に「株式・投資」が付いた。
- **制約**: このテーブルは「同じ略語で意味が違うレコードが複数ある」ことを前提に
  複合ユニークキーを持つ設計にしてある。にもかかわらず、UPDATE/INSERT の対象指定では
  その前提を無視して単一列で絞った。主タグの精緻化では両方の列を指定できていたので、
  知識の欠如ではなく、同一ファイル内での一貫性の欠如。
- **規則**: UPDATE / DELETE / 条件付き INSERT を書く前に、
  WHERE 句で使う列の組み合わせがそのテーブルのユニーク制約と一致しているか確認する。
  一致していなければ、意図した1行以外にも当たると判断する。
  実行前に同じ条件の SELECT で件数を数え、想定件数と一致しなければ止める。
- **適用範囲**: 一意制約が複合になっているテーブル全般。
  単一主キーだけで運用しているテーブルには不要。
  ORM 経由で1件ずつ処理する場合も不要（一括SQLを手書きするときに限る）。

### 主キー衝突を起こす更新は、削除を先に置く

- **症状**: `FDA` の主タグを「行政」に変更する UPDATE が
  `acronym_tags_pkey` の重複違反で失敗した。既に副タグとして「行政」が付いていた。
- **制約**: 中間テーブルの主キーが `(親ID, 子ID)` の複合になっている場合、
  子ID を書き換える UPDATE は「同じ組み合わせが既に存在しないか」に依存する。
  UPDATE 単体を見ても衝突は見えない。
- **規則**: 中間テーブルで参照先IDを書き換える UPDATE を書くとき、
  変更後の組み合わせが既存行と衝突しないか先に確認する。
  衝突し得るなら、変更先と同じ組み合わせの行を削除する DELETE を UPDATE より前に置く。
- **適用範囲**: 複合主キーを持つ中間テーブル。
  代理キー（単一の id 列）を主キーにしている場合は、
  代わりにユニークインデックス側で同じ問題が起きる。

### 前提セクションには実測だけを書く

- **症状**: Claude Code へ渡す作業指示書の「0. 前提（実測済み）」に、
  「現在のユニークキー設計では同種の重複が再発し続ける」という自分の推測を混ぜた。
  これは評価であって実測値ではない。同じ箇所で、仕様どおりの挙動を「既知の不具合」と分類した。
- **制約**: エージェントは前提として渡された内容を疑わずに実装する。
  実測と推測が同じ見出しの下に並ぶと、下流で区別できない。
  誤った前提はその後の全ての判断に伝播する。
- **規則**: 指示書の前提に1行書くたびに「これはどこで測ったか」を答える。
  答えられない行は前提から外し、現状確認タスクに移すか、推測として別見出しに置く。
  特に「〜し続ける」「〜になるはず」という将来形は実測ではない。
- **適用範囲**: エージェントに事実を渡す全ての文書。
  自分用のメモには適用しなくてよい（自分は出所を覚えている）。

### クリーニング前のデータから閾値を決めない

- **症状**: 「その他」カテゴリ18件の内訳から「学術・教育が10件あるので新設に足る」
  「昇格閾値 N=10 / 統合閾値 M=5」という結論を出した。
  しかしこのデータには、掃除用ツールの動作検証のため意図的に残された低価値レコードが混在していた。
- **制約**: 検証用に残したデータと本番データが同じテーブルに同居していた。
  「意図的に残してある」という情報がデータ側に持たれておらず、
  集計するとノイズが本番データと区別なく数えられる。
- **規則**: 件数分布から閾値やカテゴリを決める前に、
  そのデータにテスト用・検証用・意図的に残したレコードが混ざっていないか確認する。
  混ざっているなら、閾値の決定はクリーニング後に回す。
  混ざったまま決めるなら、その旨を明記して暫定値として扱う。
- **適用範囲**: 実データの分布を根拠に設計判断をする場面全般。
  構造の議論（分類を分けるか統合するか）はデータ品質に依存しないので対象外。

### 実行中のエージェントに追加入力を与えない

- **症状**: レスポンシブ対応の実装が走っている最中に、
  次のフィルタ実装の指示を投げようとした（投げる前に止めた）。
  別の場面では、実行中に手元で `app/favicon.ico` をリネームしたところ、
  エージェントが「意図しない変更」と判断して復元した。
- **制約**: エージェントは作業単位で入力を受け付けて待つのではなく、
  届いたメッセージを実行中の文脈にそのまま流し込む。
  作業ツリーの状態も同様で、自分が加えていない変更を見つけると
  無関係な混入とみなして巻き戻すことがある。
- **規則**: エージェントが完了報告を出して止まるまで、
  新しい作業指示を送らない。同じリポジトリのファイルを手元で触らない。
  進行中タスクへの補足情報（既に判断待ちで止まっている件への回答など）は例外として送ってよい。
  手元で触る必要が出たら、完了を待つか、触った旨と意図を先に伝える。
- **適用範囲**: 対話型で動くコーディングエージェント全般。
  完全にバッチで動くジョブには当てはまらない。

### 禁止事項は操作の意味ではなく実行手段を名指しする

- **症状**: 指示書に「DBを変更するSQL（DDL/DML）は実行しない」と書いたが、
  これだけでは `drizzle-kit push` や `prisma db push` を塞げない可能性があった。
  エージェントがこれらを「SQL実行」と分類しなければ、
  スキーマ定義に無い新規テーブルを DROP する提案を生成し得る。
- **制約**: 禁止を「操作の意味」で書くと、エージェント側の分類に依存する。
  同じ結果を招く別名の手段があると、字義上は禁止に触れないまま実行される。
- **規則**: 破壊的操作を禁止するとき、意味だけでなく
  実際のコマンド名・ツール名を列挙する。
  「削除しない」ではなく「DROP / TRUNCATE / db push / migrate deploy を実行しない」と書く。
  そのプロジェクトで使い得るツールを現状確認で洗い出してから禁止事項を書く。
- **適用範囲**: エージェントに破壊的操作の権限がある場面。
  読み取り専用の権限しか渡していない場合は不要。

### 遷移を伴う機能は、遷移元の扱いも完了条件に書く

- **症状**: 関連用語リンクの完了条件に「リンク先は該当レコードの詳細表示へ遷移すること」
  とだけ書いた。実装は条件を満たしたが、遷移すると背後の画面が
  逆引き一覧から検索画面に置き換わり、元の一覧に戻れなくなった。
- **制約**: 完了条件が遷移先の状態しか規定していなかった。
  エージェントは書かれた条件を満たす最短の実装を選ぶため、
  規定のない遷移元の状態は保持されない。
  ディープリンク（外部からURLで直接開く）と画面内遷移が同じ経路を使う実装になっていた。
- **規則**: 画面遷移を伴う機能の完了条件には、遷移後の表示だけでなく
  「遷移元の状態がどうなるか」「戻ったときに何が復元されるか」
  「連続して遷移できるか」を書く。
  外部からの直接アクセス経路が別に存在する場合は、両者を分けて条件を書く。
- **適用範囲**: 一覧と詳細を行き来する UI 全般。
  単一画面で完結する機能、または遷移が一方向で戻る必要がない場合は対象外。
