> summary: アクロニム辞書231件のタグ再設計と、収録可否を「知名度」でなく「その文脈で誤読が起きるか」で判定する基準の確立

# アクロニム辞書のタグ再設計と収録基準

対象：itachi-p/my-acronym-app（2026-09-03〜04）

## 背景

旧6分類（ビジネス・経営／金融・株式／政治・行政／軍事・安全保障／IT・テクノロジー／その他）から
19タグの複数付与方式へ移行した際、移行前のレコードは旧カテゴリから機械変換された主タグ1個だけの
状態で残っていた。231件全件について主タグの妥当性を見直し、サブタグを付け直す作業から始まった。

---

## 判断

### 1. タグ構造は「主タグ1＋サブタグ最大2」（採用）

1レコードあたり最大3タグ。表示・検索の一貫性を保ちつつ、旧1:1対応では表現できなかった
分野横断の語（DARPA＝軍事×IT×学術など）を扱えるようにするため。

結果：主タグ変更13件、サブタグのみ変更113件、変更なし105件。タグ総数 354→489。

### 2. 主タグは「役職語は役職として」揃える（採用）

CIO(Chief Investment Officer) が株式・投資、他のC-level（CEO/CFO/COO/CTO/CIO情報）が組織・人事
という不統一があった。役職語は全て組織・人事を主タグにし、領域はサブタグで表現する形に統一。

根拠：語の性質（役職である）と語の領域（投資である）は別の軸であり、主タグは前者を担う方が
分類の予測可能性が高い。

### 3. 「その他」に残った語は分類不能ではなく受け皿の不在（採用・ただし対処は保留）

その他6件のうち ABS(アンチロックブレーキ)・GPU(地上電源装置)・DIY は、
分類できないのではなく「工学」タグが存在しないために滞留していた。
同様の穴が 法律（SPA / USA PATRIOT Act / MIT License）、
エネルギー・環境（OPEC / ESG / EV）、心理（FOMO / MBTI / NLP）にもある。

**工学タグの新設は保留。** タグを増やすと辞書のスコープが広く見え、
「経済・経営を主軸とする」という位置づけが曖昧になる副作用があるため。
問題の所在だけ記録し、判断は先送りする。

### 4. 収録可否は「知名度」でなく「その文脈で誤読が起きるか」で判定（採用）

これが今回いちばん再利用価値のある基準。

| 語 | 判断 | 根拠 |
|---|---|---|
| CRT = Cathode Ray Tube | 破棄 | 世代的な知名度は高いが、経済・経営の話に出てこないので取り違えようがない＝ホモニムとして仕事をしない |
| CRT = Critical Race Theory | 採用 | 差別・社会現象の系列（KKK / GBV / CEDAW / FGM）に接続する |
| EV = 電気自動車 | 残す | 誰でも知っているが、経済の話に頻出するからこそ Enterprise Value / Expected Value との取り違えが起きる |
| ROI = Region of Interest | 残す | 同型（本命が経営語、ホモニムが技術用語） |
| SMART = ストレージ自己診断技術 | 残す | 同型 |
| LSI | 不採用 | 今の経済語彙は半導体／チップ／ファウンドリで、LSIは出てこない |
| UDE = ドイツの大学 | 破棄 | 「文脈で説明なしに出る大学名」に該当しない |

従来の中心テスト「知らないと文意が取れないか」だけでは EV=電気自動車 は落ちる。
しかし辞書の機能は「未知語の解読」だけでなく「既知語の取り違え防止」でもあり、
後者を評価軸に加えると判断が反転する。両方の軸で見る。

### 5. EC = Electronic Commerce を追加（採用）

TOCの EC(Evaporating Cloud) を登録するにあたり、日本語のビジネス文脈で「EC」は
まず電子商取引と読まれることに気づいた。「Eコマース」という展開形は死語化した一方、
略語のECだけが ECサイト / EC化率 / EC事業 として定着している
（展開形より略語が長く生き残った例）。基準4により追加。

### 6. TOC思考プロセスは8語採用、TT は破棄（採用→部分撤回）

UDE / CRT / EC / ATT / FRT / PRT / TT / CLR の8語を追加。
うち TT(Transition Tree) は TOC内でも使用頻度が低く、かつ2文字略語であるため不要と判断。
**差分SQLを作り直さず、適用後に1文で手動削除する方針を採用。**

根拠：SQLの再生成に費やすトークンより、適用後の1行DELETEのほうが安い。
関連語リンク未作成・他の説明文からの参照なしを確認した上での判断。

### 7. 削除語を rejected_candidates に登録しない（採用）

同テーブルは acronym に一意索引がある。'UDE' / 'CRT' を弾く登録をすると、
同時に入れる UDE=Undesirable Effect / CRT=Current Reality Tree まで
将来の自動登録経路でブロックされる恐れがある。
再登録防止はAI判定プロンプト側で対処すべき問題と切り分けた。

### 8. 企業名・2文字略語の例外を明示（採用）

- TSMC / ASML：「企業名は原則不可」の例外。経済安全保障の議論がこの2社の固有名でしか
  成立しないため。BBC / FDIC と同じく「何であるか」で分類する。
- IC / PV / GX / DX：「2文字は原則不可（許可制）」の例外。手動登録ルートは
  開発主の意思決定が前提なので、AI判定基準の対象外として通す。

### 9. 半導体・エネルギー環境・通商・デジタル基盤 33語を追加（採用）

WTO / IoT / GPS / DX のような基本語すら未登録だったことが判明。
ZEH / ZEB / NDC / RE100 / BESS は補助金や制度の細部に寄るため保留。

### 10. 3本目のSQLから「件数の前提を置かない」設計へ変更（採用）

1〜2本目は事前チェックで件数（231件 / 235件）を固定していたため、
アプリ経由で1件でも追加されると実行できなくなる。
3本目は重複を自動スキップする形にして、適用順や中間状態に依存しない冪等なSQLにした。

## 経緯

### データ取得の制約と回避

本番DB（Neon）へ直接接続できず、ブラウザのSQL Editor経由でしか読めない状況だった。
231件×説明文を結果グリッドから読み出すために、

1. SQLで20件ずつを1セルに集約して12行に圧縮
2. 結果グリッドのDOMからテキストを取得
3. JS実行結果に約1,250字の上限があったため、850字ずつスライスして回収

という手順を取った。素直に1行ずつ読むより往復回数が1桁少ない。

### full_spelling の照合が壊れる問題

231件を (acronym, full_spelling) で照合する設計にしたが、データ側に
`Don’t Repeat Yourself`（U+2019）、`Retrieval‑Augmented Generation`（U+2011）、
キリル文字、`Dirección`、`Karkerên` といった非ASCII文字が含まれていた。
自分が読み取った文字と実データの文字コードが一致する保証がない。

対処：非ASCII文字とアポストロフィを `_`（LIKEの任意1文字）に置換したパターンで照合。
併せて「231件すべてがちょうど1件にマッチすること」を事前チェックに入れ、
1件でも外れたら例外で全体ロールバックする構成にした。

### RAISE の書式指定子バグ（失敗記録）

1本目はPythonの文字列フォーマットでSQLを生成したため `%%` が `%` に変換されたが、
2本目はヒアドキュメントで直接書いたため `%%` がそのまま残り、
`too many parameters specified for RAISE` で全体が失敗した。

ローカル検証で検出。**検証していなければ本番で失敗していた。**
ただしトランザクション設計により実害はロールバックで止まる範囲だった。

## 検証

コンテナ内にPostgreSQL 16を立て、本番と同じスキーマ・同じ231件・同じタグ354本を
再現したレプリカを作って全SQLを実行した。確認項目：

- 適用後の全231件のタグ集合が設計と完全一致（差分ゼロ）
- 2回流しても結果が変わらない（冪等）
- 主タグ1つ / 最大3タグ / acronyms.category 同期の不整合ゼロ
- 前提件数が違う場合に事前チェックで止まること

その後の追加分も、本番の現状（235件 / 495リンク）に追い付かせたレプリカで同様に検証した。

## 学び

- **「知らないと文意が取れないか」は必要条件だが十分条件ではない。**
  辞書の機能を「未知語の解読」と「既知語の取り違え防止」の2つに分けると、
  同じ語でも判断が反転する。単一の中心テストで運用すると後者を取りこぼす。

- **展開形が死語化しても略語だけが生き残る現象がある**（Eコマース→EC）。
  略語辞書としては、展開形の使用頻度ではなく略語の使用頻度で判定すべき。

- **移行スクリプトの機械変換は歪みを残す。**
  旧6分類→19タグの一括変換で13件の主タグが不適切になっていた。
  変換の直後に全件レビューを挟まないと、以後は「そういうもの」として固定される。

- **本番と同じ状態のレプリカを立てて実行するコストは、書式指定子1個のバグを
  拾えた時点で回収できている。** 特に生成方法（テンプレート経由か直書きか）が
  途中で変わったときにこの種の差分が入る。

- 一意索引の副作用は、そのテーブル単体でなく「将来入れたい語」まで含めて確認する
  （rejected_candidates の件）。

## 次の課題・接続先の仮説

- **AI判定プロンプトへの基準の組み込み。** 現状の登録ロジックは略語の事実的妥当性は
  検証するが、話題的関連性を検証していない。「経済・経営の文脈に出る語義か」を
  Groqへのプロンプトに入れれば、CRT=ブラウン管のような巻き添えが入口で減るはず。
  → 検証可能な仮説：判定プロンプトに文脈条件を足すと、意図しないホモニムの混入率が下がる

- **タグ体系の穴（法律・工学・エネルギー環境・心理）をどう埋めるか。**
  タグ追加はスコープ拡大に見える副作用がある。増やす／増やさないの判断材料が足りていない。

- **acronym_relations による TOC語彙の相互リンク。**
  UDE / CRT / FRT / PRT / CLR は単体では意味が取れず、思考プロセスの手順として
  繋がって初めて機能する。リンクなしで置くと死蔵する可能性が高い。

- 適用済みSQLの保管場所を `db/history/` に分離した。
  `db/` 直下（schema.sql / seed.sql）は「現在の姿」、`db/history/` は「適用の記録」という切り分け。
